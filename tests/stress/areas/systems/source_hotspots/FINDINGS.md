### WRONG-1 — `groebner` silently drops polynomials past the 256th (`part[256]`)
**Severity:** WRONG
**Expected:** _not recorded_
**Why it matters:** _not recorded_
`src/absalg_cmd.c:2024-2032` calls `split_commas(s, part, 256)` and loops `i < n`.
`split_commas` (`src/absalg_cmd.c:55-75`) increments `n` **only while `n < max`**, so it returns 256
for a longer list: the surplus polynomials are never parsed, with no diagnostic.

Exact reproducer (creates a 257-item list whose **last** item changes the answer):

**Reproducer:**
```sh
cd /tmp
python3 -c "print('groebner '+','.join(['x^2']*256)+', x')" > g257.ucas
timeout 15 $ROOT/ucas g257.ucas
# control: 255 x^2 followed by x  -> the 256th item IS read
python3 -c "print('groebner '+','.join(['x^2']*255)+', x')" > g256.ucas
timeout 15 $ROOT/ucas g256.ucas
```

**Observed:**

```
# 257 items (256*x^2, x):
reduced Groebner basis (grevlex, x, over Q): 1 element
  g1: x^2
pairs: 32640; reduced: 255; ...
# 256 items (255*x^2, x):
reduced Groebner basis (grevlex, x, over Q): 1 element
  g1: x
```

`x` is in the ideal generated by the 257 listed polynomials, so the correct reduced basis is
`x`, not `x^2`. The 257th input is silently discarded. The echoed `> groebner ...` line still
contains all 257 items, which makes the omission invisible to the user. Same behaviour for
`idealmember` / `idealeq` (the other `need_polys` callers). Kept as goldens:
`08_arrays_groebner.ucas`, `09_arrays_groebner_over.ucas` (the 256/257 boundary, innocuous
inputs only).

### WRONG-2 — `pmsnf` silently drops rows past the 64th (`rows[64]` / `cells[64]`)
**Severity:** WRONG
**Expected:** _not recorded_
**Why it matters:** _not recorded_
`src/absalg_cmd.c:2263-2296`: `nr = split_commas(body+1, rows, 64)`, then `pm_init(&A, nr, nc)`
and `for (i = 0; i < nr; i++)`. The extra rows never reach the matrix.

**Reproducer:**
```sh
cd /tmp
python3 -c "print('pmsnf ['+','.join(['[x]']*64)+',[1]]')" > p65.ucas
timeout 15 $ROOT/ucas p65.ucas
# control: 63 [x] rows + [1]  -> 64 rows, all read
python3 -c "print('pmsnf ['+','.join(['[x]']*63)+',[1]]')" > p64.ucas
timeout 15 $ROOT/ucas p64.ucas
```

**Observed:**

```
# 65 rows: Smith form over Q[x]: diag(x), rank 1
# 64 rows: Smith form over Q[x]: diag(1), rank 1
```

The 65th row `[1]` is dropped, leaving a wrong Smith form. No warning is emitted.
Goldens: `10_arrays_pmsnf.ucas`, `11_arrays_pmsnf_over.ucas`.

Related, same root cause: `absub` / `permhom` use `part[64]` (`absalg_cmd.c:1112,1767,1780`);
`abgroup Z/2 + …` with 70 factors and `absub` with 70 vectors returned rc 0 with no diagnostic
(`12_arrays_abgroup.ucas` golden). No OOB write: `split_commas` caps `n` before the write, so
the IDEAS_SOURCE #10/#22 stack-overflow premise does **not** reproduce in this build — the
observable defect is silent truncation, not a crash.

### DETERMINISM-1 — `clock()` deadlines make `rules infer` results machine-load dependent
**Severity:** DETERMINISM
**Expected:** _not recorded_
**Why it matters:** _not recorded_
`src/find.c:632,3534` stop the search on `clock() > F.deadline`. A fixed `seconds 1` budget yields
a different number of candidates and a different rule set depending on CPU contention.

**Reproducer:**
```sh
cd /tmp
printf 'rules infer inputs 3 width 16 seconds 1\n' > infer.ucas
timeout 15 $ROOT/ucas infer.ucas > idle.out 2>&1
for i in 1 2 3 4; do (while :; do :; done) & done   # add CPU load
timeout 15 $ROOT/ucas infer.ucas > load.out 2>&1
kill %1 %2 %3 %4 2>/dev/null
diff idle.out load.out
```

**Observed:** (two consecutive runs, idle vs 4 busy loops):

```
idle: 3342 candidates ...; 423 read: 75 kept, 222 derived from the kept ones,
      33 priced alike by the cover, 93 made one by the constructors, 0 not proved equal; out of time
load: 3342 candidates ...; 408 read: 71 kept, 215 derived from the kept ones,
      29 priced alike by the cover, 93 made one by the constructors, 0 not proved equal; out of time
```

and the idle run contains rules `r72..r75` (e.g. `r73 = a + b - b => a`) that the loaded run
never emits. Consequence: golden tests using `rules infer`, `snippets grow`, `find … stoke` with
a wall-clock cap are flaky. Such cases are documented here only, not kept as goldens; the kept
`06_clock_short.ucas` uses a small enumeration that finishes before the deadline and is
byte-stable across runs.

### DETERMINISM-2 — failed GLSL compilation embeds a random `/tmp/ucas-glsl-XXXXXX.glsl` path
**Severity:** DETERMINISM
**Expected:** _not recorded_
**Why it matters:** _not recorded_
The diagnostic text is not stable between processes, so any golden that exercises a GLSL compile
error will fail a diff.

**Reproducer:**
```sh
cd /tmp
python3 - <<'PY'
f = chr(96) * 3
open('glslerr.ucas','w').write('simplify nofile\n' + f + 'glsl\n' +
  'float f(){ struct A { struct B { float x; } b; } a; return a.b.x; }\n' + f + '\n')
PY
timeout 15 $ROOT/ucas glslerr.ucas   # run twice
```

**Observed:**

```
run 1:  ERROR: /tmp/ucas-glsl-jqev84.glsl:1: '' : cannot nest a structure definition inside a structure or block
run 2:  ERROR: /tmp/ucas-glsl-3vTpPW.glsl:1: '' : cannot nest a structure definition inside a structure or block
```

Only the mkstemp suffix differs; the underlying GLSL rejection is correct. No golden kept.

### DETERMINISM-3 — MCP `animate` uses a fresh random seed unless `seed` is given
**Severity:** DETERMINISM
**Expected:** _not recorded_
**Why it matters:** _not recorded_
The `plot`/`animate` MCP tool with no explicit `seed` prints a different "buffers start with
random values (seed N)" line and a different GIF checksum on every process start, even though
the CLI `animate` defaults to seed 1.

**Reproducer:**
```sh
cd $ROOT/tests/stress/areas/systems/source_hotspots
# a jsonl with an animate tools/call that omits "seed"
timeout 15 $ROOT/ucas --mcp < mcp_img_decode.jsonl
```

**Observed:** with the seed omitted (before the golden was pinned):

```
run 1: "buffers start with random values (seed 57208)" ... "(nofile: GIF checksum 83cf818c)"
run 2: "buffers start with random values (seed 57209)" ... "(nofile: GIF checksum 9d40569e)"
```

With `"seed":1` in the arguments the output is byte-identical across runs; that is how the kept
`mcp_img_decode.jsonl` golden is pinned. Recommend always passing `seed` in MCP animate goldens.

### LIMIT-1 — the `strcat` engine buffer and the two recursion caps are already guarded (no overflow/crash)
**Severity:** LIMIT
**Reproducer:** _not recorded_
**Observed:** _not recorded_
**Expected:** _not recorded_
**Why it matters:** _not recorded_
IDEAS_SOURCE items #8, #12 expected a fixed-buffer overflow / stack overflow. In this build the
dangerous writes are bounded, and 2000-deep probes returned cleanly:

* `src/cf_opt.c:1864-1868` checks `strlen(w->engine) + strlen(s[k].engine) + 2 < sizeof w->engine`
  before the two `strcat`s (`w->engine` is `char[16]`). Engines beyond the 16-byte budget are
  skipped, so the engine string is truncated but cannot overflow. `c optimize` does not expose
  the engine string in text or `structuredContent` (`proof` / `proof_text` only), so no user-visible
  WRONG was produced. Probes: `04_engine_chains.ucas`, `05_long_ident.ucas` (3000-char C identifier),
  `mcp_engine_longid.jsonl` (2000-char identifier) — all rc 0, stable.
* `src/spirv.c:8755` has `if (depth > 24) return -1;` in `fx_build`; `src/snxglslc/emit.c:823` has
  `if (depth > 32) return 0;` in `emit_constant`. `16_recursion_spv.ucas` (40 chained
  `OpCopyObject`/`OpCompositeExtract`) and `17_recursion_spv_long.ucas` (2000 chained) both
  returned rc 0 with a clean "nothing to rewrite" message. `14_recursion_parens.ucas` (5000-deep
  GLSL parens) and `15_recursion_struct.ucas` (1000 nested `abs` calls) also rc 0.
* `src/lex.c:113-120` does swallow the rest of a word after `file` as a path, but in the
  `animate exec … input N file PATH` context the path is only read; odd paths
  (`/dev/null`, `/etc/hostname`, `.`, `..`, `../…`, spaced names) produced clean `error:` messages,
  never a read or a hang. Goldens: `18_file_paths.ucas`, `19_file_paths_direct.ucas`.
  (Arbitrary path *acceptance* is already catalogued in `tool_abuse_files`; not re-reported as new.)

### LIMIT-2 — image decoders reject malformed/truncated bytes cleanly (no crash)
**Severity:** LIMIT
**Expected:** _not recorded_
**Why it matters:** _not recorded_
143 crafted/mutated files (43 malformed PNG/GIF/JPEG/BMP/PNM plus 100 seeded random byte
mutations of valid PNG/GIF/JPEG) were fed through the `animate exec … input 1 file …` decode path
with a real `OpImageSampleImplicitLod` shader, each under `timeout 15`. **All returned rc 0** with a
clean `error:` line; no signal, no hang, no truncated output. Dimension caps are enforced:

**Observed:**
**Reproducer:**
```sh
img/bmp_huge.bmp: BMP: 2147483647x1 is over the cap (16384 per side, 24 Mpixels)
img/ppm_huge.ppm: PNM: 100000x100000 is over the cap (16384 per side, 24 Mpixels)
img/huge.png:     PNG: not an image I can read
img/trunc50.png:  PNG: the file is truncated
```

Goldens `20_img_malformed.ucas`, `21_img_valid.ucas`, `mcp_img_decode.jsonl` pin the clean
errors and two stable checksums. Minor message bug: a 6-byte GIF that declares a 0x0 canvas is
reported as `GIF: 0x0 is over the cap (16384 per side, 24 Mpixels)` rather than "invalid size".

### WRONG-3 — no stale-frame failure reproduced
**Severity:** WRONG
_Original classification: `WRONG (longjmp path`._
**Reproducer:** _not recorded_
**Observed:** _not recorded_
**Expected:** _not recorded_
**Why it matters:** _not recorded_
IDEAS_SOURCE #5 suspected that a `longjmp` from a nested callback could reach a stale frame.

`mcp_longjmp_session.jsonl`. No bug to report; the error/unwind path behaved correctly in this
build.
