# Stress findings — `lexer_army`

# FINDINGS — `lexer_army`

Front-end mining wave 2: tokenizer edge cases and JSON string output. All
goldens were generated by the fixed binary under the canonical environment
(`UCAS_NO_TIMES=1 UCAS_SPIRV_CROSS=none`) from this directory.

## Summary

| Severity | Count | One-line headline |
|----------|-------|-------------------|
| WRONG | 3 | `file` as an identifier swallows the next operator; invalid binary digits are silently ignored; invalid UTF-8 leaks into JSON replies |
| HANG | 1 | a long identifier takes quadratic time in symbol interning |

## Findings

### WRONG-1 — the `file` path rule corrupts ordinary expressions

**Severity:** WRONG
**Source:** `src/lex.c`

The "the path after `file` is one word" special case was applied to any
non-space character following a `file` token, not only to a plausible path.
`file` is otherwise a valid identifier, so operators after it were swallowed
into one identifier token:

```
$ printf 'file(x) = x + 1\n' | ucas
_(file: real, (x): real, x: real) = file*(x) == x + 1     # before
$ printf 'file = 3\n' | ucas
_(file: real, =: real) = 3(file*=)                        # before
```

`parse file(1)` read `(1)` as a variable named `(1)`, and `parse file+x`
became `(file * +x)`.

**Fix:** require the next character to be a path-start character (alphanumeric
or `/ . _ ~`) and the word to be at least two bytes; otherwise the operator is
left to the normal scanner. Golden `01_file_identifier.ucas` now shows the
correct `(file + x)`, `(file * x)` and clean definitions. The real
`input N file a/b.png` command is preserved by `02_file_path_control.ucas`
(and by the pre-existing `images.out` / `source_hotspots` goldens, which are
unchanged).

### WRONG-2 — invalid binary digits silently truncated

**Severity:** WRONG
**Source:** `src/lex.c` (number scanning) with `src/parse.c` (`strtoull` base 2)

The lexer consumed any hex digit after `0b`, but the parser used
`strtoull(buf + 2, NULL, 2)` and ignored the end pointer. Invalid digits were
therefore dropped instead of reported:

```
parse 0b102       -> 2       (silently read as 0b10)
parse 0b1f        -> 1
parse 0bdeadbeef  -> 0
```

**Fix:** validate every digit of a binary literal at lex time and fail at the
offending byte with `invalid digit 'X' in a binary literal`. Golden
`03_binary_bad_digit.ucas`. Valid binary/hex literals are a control in
`04_binary_good_control.ucas`.

### WRONG-3 — JSON/MCP replies were not valid UTF-8

**Severity:** WRONG
**Source:** `src/json.c` (`json_quoten`)

The JSON string writer copied bytes >= 0x80 verbatim. Raw invalid UTF-8 in a
request string was echoed into the reply, so a strict UTF-8 JSON client could
not parse it:

```
printf '{"id":1,"cmd":"show","args":{"f":"a\xffb"}}\n' | ucas --json
# -> "ucas": "show a\xffb"    (raw 0xff)
```

This also affected the echoed `cmd` and error messages, and the MCP
`tools/call` path (a layer over the JSON frontend).

**Fix:** `json_quoten` now validates each UTF-8 sequence (rejecting overlong
forms, encoded surrogates and code points past U+10FFFF). Invalid bytes are
emitted as `\u00XX`, so replies are always valid UTF-8 JSON. Valid UTF-8
(2-, 3- and 4-byte sequences) is copied through unchanged.
`json_invalid_utf8.jsonl` covers 0xff, an overlong `\xc0\xaf`, an encoded
surrogate `\xed\xa0\x80` and an out-of-range `\xf4\x90\x80\x80`;
`json_utf8_control.jsonl` is the passthrough control.

### HANG-1 — long identifier quadratic slowdown

**Severity:** HANG
**Source:** quadratic cost in symbol interning (`src/util.c:sym_intern`);
bounded in `src/lex.c` (the owned file)

A bare run of ASCII letters made a statement take time proportional to the
square of its length (20K letters about 2.9 s, 200K about 4.9 s and still
growing). Callgrind attributes ~95% of the run to `sym_intern`/`fnv`, where
the long name is hashed once per use.

**Fix:** cap an identifier (and a `file` path word) at 4096 bytes in the
lexer, failing with `identifier too long (over 4096 bytes)` at the offending
position. 200K letters now fail in ~0.04 s. Golden `05_ident_cap.ucas`;
`06_ident_control.ucas` (200 letters) is the control.

## Checks that passed

- Unicode operator folding (`07_unicode_ops.ucas`): `× ÷ ≤ ≥ ≠ √ ² ³ °`
  are unchanged and evaluate as before.
- Valid binary and hex literals (`04_binary_good_control.ucas`).
- The `input N file PATH` command (`02_file_path_control.ucas`).
- Valid UTF-8 strings in JSON requests (`json_utf8_control.jsonl`).
- No crashes, hangs or out-of-bounds reads in ~2500 random byte/JSON inputs
  and in the targeted unicode boundary matrix from the unicode fuzzing run.
