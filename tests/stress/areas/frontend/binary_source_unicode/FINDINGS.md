# Findings — `binary_source_unicode` stress area

Focus: non-ASCII and control bytes in source and English input (ideas 2, 5, 6
of `IDEAS_UNDERGROUND.md`, plus the full math/Unicode sweep).
Binary: `$ROOT/ucas`. Every CLI run was bounded with
`timeout 15`; MCP/JSONL and JSON goldens with `timeout 15` as well.

**Counts:** 172 independent stdin cases (`run_cases.sh`), 20 focused stdin
cases (`run_stdin.sh`), 10 CLI-file goldens, 4 MCP/JSONL goldens (34 calls) —
**~236 distinct cases**. All goldens were generated by running each case twice
and keeping only byte-identical outputs (`cmp`), then verified with the exact
commands from `tests/stress/run.sh`. No case crashed, hung, or differed between
runs; determinism was clean everywhere.

## Findings

### WRONG-1 — NUL byte silently truncates source; the truncation rule differs per frontend
**Severity:** WRONG
parser differential). This is idea 2, confirmed and extended.

#### 1a. File mode: a NUL truncates the *entire rest of the file*

**Reproducer:**
```sh
printf 'show 1+2\000show 3+4\nshow 5+6\n' > /tmp/nul.ucas
timeout 15 $ROOT/ucas /tmp/nul.ucas
```
**Observed:** (only the first statement runs; `show 3+4` and `show 5+6` vanish):
```
> show 1+2
_() = 3
  -> int
```
A clean file with the same three statements produces all three results. The
NUL is treated as end-of-input, so everything after it on *all* lines is
silently discarded. Golden `01_nul_lines.ucas/.out` (15 lines, only line 1
survives) captures this.

#### 1b. Stdin mode: a NUL truncates only the *current line*

```sh
printf 'show 1+2\000show 3+4\nshow 5+6\n' | timeout 15 $ROOT/ucas
```
**Observed:** (`show 3+4` dropped, but the following line still runs):
```
_() = 3
  -> int
_() = 11
  -> int
```
So the *same source* yields different results in file mode (one statement)
and stdin mode (two statements). A parser differential driven purely by a
single 0x00 byte.

#### 1c. English request silently loses its meaning

```sh
printf 'is 1\000 even?\n' | timeout 15 $ROOT/ucas
```
**Observed:**
```
  ucas: 1
1
```
The request "is 1 even?" is truncated to `is 1`, which is no longer recognised
as a question, and is silently reinterpreted as the bare expression `1`
(`understood`-style output with no error). The `even?` predicate is lost.

#### 1d. Keyword silently becomes an identifier (fabricated definition)

```sh
printf 'sho\000w 2+2\n' | timeout 15 $ROOT/ucas
```
**Observed:**
```
_(sho: real) = sho
  -> real
```
`show` is truncated to `sho`, which is parsed as a free variable; the command
degenerates into a bogus anonymous definition. Same mechanism turns
`show ab\0cd` into `_(a: real, b: real) = a*b` (a note claims `ab` was "read
as a*b"), and `f\0oo(x)=x` silently discards the intended definition of `foo`.

#### 1e. JSON / MCP: escaped NUL loses the whole request and its id

```sh
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"ucas","arguments":{"source":"show 1+2\u0000show 3+4"}}}' \
  | timeout 15 $ROOT/ucas --mcp | tail -1
```
**Observed:**
```
{"jsonrpc": "2.0", "id": null, "error": {"code": -32700, "message": "parse error"}}
```
The JSON is well formed, so `-32700` is the wrong code, and the legitimate
`id:1` is discarded (see `mcp_unicode_source.out` ids 1 and 8). This is the
same root cause as `mcp_api_fuzz` finding 2 but reached through the `source`
argument rather than a tool name.

**Why it matters:** a bug:** a single control byte changes semantics, silently drops
statements, fabricates definitions, and produces three different behaviours in
three frontends.
**Expected:** reject NUL with a clear error and preserve the
request id, or handle it identically everywhere.

### WRONG-2 — invalid UTF-8 emitted inside JSON/MCP output
**Severity:** WRONG
consumer). Ideas 5/6 confirmed at the output layer.

The English frontend's error message `I can't read the character 'X'` copies
only the **first byte** of the offending multi-byte UTF-8 character, producing
a bare lead byte that is not valid UTF-8. The MCP and `--json` frontends embed
that raw byte directly in a JSON string.

**Reproducer:**
```sh
cd $ROOT/tests/stress/areas/frontend/binary_source_unicode
timeout 15 $ROOT/ucas --mcp < mcp_unicode_english.jsonl > /tmp/u.out
python3 -c 'import json; d=open("/tmp/u.out","rb").read();
print([json.loads(l) for l in d.splitlines()])'
```
**Observed:** (Python aborts on line 2):
```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe2 in position 129: invalid continuation byte
```
The raw bytes appear four times per affected response (in
`content[0].text`, `structuredContent.text`, `structuredContent.error.message`,
and the nested text). Examples from `mcp_unicode_english.out` and
`json_unicode.out`:
```
... I can't read the character '\xe2'\n      <- U+202E RLO (E2 80 AE) truncated to E2
... I can't read the character '\xf3'\n      <- Tags-block U+E0061 (F3 A0 81 A1) truncated to F3
... I can't read the character '\xf0'\n      <- math-bold U+1D431 (F0 9D 90 B1) truncated to F0
```
`mcp_unicode_english.out` contains **17** such invalid lead bytes;
`json_unicode.out` contains 3. It also happens on plain CLI stdout:
```sh
printf 'is \342\200\256X\342\200\254 even?\n' | timeout 15 $ROOT/ucas | od -An -tx1
#   ... 69 73 20  e2  20 65 76 65 6e 3f ...      (bare 0xE2)
```
**Why it matters:** a bug:** a compliant JSON-RPC client that parses response bytes as UTF-8
will reject these replies.
**Expected:** emit U+FFFD (`\ufffd`) or `\uXXXX` escapes,
or the full original bytes — never a truncated sequence.

### NLP-1 — bidi/format controls echoed raw into error messages (Trojan-Source display confusion)
**Severity:** NLP
_Original classification: `NLP / LIMIT`._
Bidi overrides, zero-width marks, BOM, soft hyphen and the Tags block are
correctly rejected in source, but the diagnostic reproduces the raw control
bytes verbatim in the caret line, so what a terminal *displays* is not what the
parser consumed:

**Reproducer:**
```sh
printf 'show \342\200\256X\342\200\254\n' | timeout 15 $ROOT/ucas
```
**Observed:** (U+202E/U+202C are invisible/reordering; the line is echoed with
them intact):
```
<stdin>:1:6: error: unexpected character '?'
    show ‮X‬
         ^
```
With RLO the displayed token order can be reversed relative to the bytes that
were actually parsed — the classic CVE-2021-42574 confusion. Same for
`LRE/RLE/LRO/PDF/LRM/RLM/ZWSP/ZWNJ/ZWJ/WJ/SHY/BOM` (golden
`02_bidi_identifiers.out`) and the Tags block (`04_tags.out`, e.g. a
hidden `TAG_a` before `x` renders as an ordinary `x` in the caret line).

A related silent-misparse: a bidi mark inside a definition name makes the
definition fail, but a later use still emits a misleading line:
```sh
printf 'f\342\200\217(x)=x\nshow f(3)\n' | timeout 15 $ROOT/ucas
#   ... error: unexpected character '?'
#   note: f(...) read as multiplication: f is not a function
# _(f: real) = 3f
```
The user's definition vanished and a wrong-looking `_(f: real) = 3f` remains.

**Why it matters:** notable:** invisible characters are echoed unescaped into diagnostics,
so a reviewer reading the error cannot see which bytes were rejected.
**Expected:**
escape control/format code points in error output.

### NLP-2 — math-symbol normalization is asymmetric across symbols and frontends
**Severity:** NLP
_Original classification: `NLP / LIMIT`._
**Reproducer:** _not recorded_
**Observed:** _not recorded_
**Expected:** _not recorded_
There is no consistent policy for mathematical Unicode. Some code points are
silently normalized to ASCII and answered; others are rejected, and the two
frontends disagree:

Accepted (silently mapped):
- English: `≤ ≥ ≠ √ ∞ − × ÷ °` — e.g. `is 1 ≤ 2?` → `ucas: 1 <= 2` / `1`;
  `what is √ 16?` → `sqrt(16)` / `4`; `is 1 < ∞?` → `1 < inf` / `1`;
  `show °` → `0.01745329252 -> real` (degrees→radians).
- CLI source: `≤ ≥ ≠ √ × ÷ −` are recognised as *operators*: `show 2×3` → `6`,
  `show 6÷3` → `2`, `show 3−1` → `2`, `show ≤` → `error: expected an expression`
  (operator with no operand).

Rejected: `∫ ∑ ∏ ≈ ∈ ∀ ∃ ∂ ∇ ℝ ± ′` and all CJK/Cyrillic/Greek names as
characters (e.g. `what is ∫ x from 0 to 1?` → `sorry: I can't read the character ...`).

Frontend divergence: `∞` is accepted in English but rejected in CLI source
(`show ∞` → `unexpected character '?'`); `−`/`×`/`÷` are accepted in both;
`∂` produces a different message (`I didn't expect '∂' here`) than `∫`
(`I can't read the character ...`). Golden `08_math_symbols.out` and the
`math *` cases in `cases_all.out` capture the whole sweep.

**Why it matters:** a bug / notable:** identical-looking mathematical operators are silently
given different meanings (or none) depending on code point and frontend. A
confusable that maps to a *different* operator would be a WRONG; as tested the
mappings are semantically correct, so this is documented as an inconsistency,
not an unsoundness.

### NLP-3 — control characters in English text: CLI accepts + echoes raw, JSON/MCP reject
**Severity:** NLP
_Original classification: `NLP / LIMIT`._
**Why it matters:** _not recorded_
**Observed:**
**Reproducer:**
```sh
# CLI stdin: accepted, raw ESC echoed in the error
printf 'is 1 \033[31m even?\n' | timeout 15 $ROOT/ucas | od -An -tx1
# ... 69 73 20 31 20  1b  5b 33 31 6d ...
```
```
  sorry: I can't read the character '<ESC>'
```
But the same text through JSON and MCP is rejected up front:
```sh
printf '%s\n' '{"id":1,"cmd":"english","args":{"text":"is 1 \u001b[31m even?"}}' \
  | timeout 15 $ROOT/ucas --json --files none
```
```
{"id": 1, "ok": false, "cmd": "english", "error": {"code": "bad_request", "message": "text: one line of ucas text, without newlines, control characters or '#'"}}
```
The CLI path both accepts the input and writes a raw 0x1B into its output; the
structured frontends refuse it.
**Expected:** one consistent rule across all
frontends, and escaping of control bytes in messages.

### LIMIT-1 — CR (0x0D) in source acts as a statement separator
**Severity:** LIMIT
**Expected:** _not recorded_
**Why it matters:** _not recorded_
**Reproducer:**
```sh
printf 'show 1\r2\n' | timeout 15 $ROOT/ucas
```
**Observed:**
```
_() = 2
  -> int
```
A bare carriage return splits `show 1` and `2` into two statements (the last
result wins), whereas BOM/CR-only line handling is a separate
encoding concern. Mixed CR/LF files can therefore split statements differently
from LF-only files. No hang or crash.

## Checks that passed

### Checked, no issue found (negative controls)
- **Combining-mark bomb**: `show x` + U+0301 repeated 5 000 and 20 000 times
  under `timeout 15` completed in ~19 ms / ~10 ms (exit 0, no hang), echoing
  the raw marks in the error caret. Idea 21 does **not** reproduce here.
- **Invalid UTF-8 input** (lone continuation 0x80/0xFF, overlong C0 AF,
  truncated E2 80, CESU-8 surrogate ED A0 80, 5-byte F8 lead, lone C2) is
  rejected gracefully with `unexpected character '?'` / "can't read the
  character"; no crash or OOB read (`09_invalid_utf8.out`, `utf8 *` cases).
- **Tool names / args with homoglyphs or bidi** (`an\u0430lyze`, `\u202eenglish`,
  `englis\u202eh`, argument key `tex\u202et`) are rejected as
  `-32602 unknown tool` / `english has no argument ...`; the raw characters are
  correctly JSON-escaped as `\u202e`, and no tool silently defaults to another
  (`mcp_tool_names.out`).
- **Tags-block invisible instruction payload** (idea 6) is always rejected;
  no invisible character alters a token or definition (`04_tags.out`).
- **NUL-in-tool-name** / NUL-in-argument remain `-32700` with `id:null`
  (`mcp_unicode_source.out`), consistent with `mcp_api_fuzz`.
- All Unicode/homoglyph/bidi/tag inputs returned exit 0 within the timeout;
  **no CRASH and no HANG** was found in this area.
